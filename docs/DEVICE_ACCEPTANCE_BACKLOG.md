## 1. 执行约定

1. 后续功能开发及相应单元、接口、浏览器检查继续，不把逐轮手机安装、截图或点击验收当作前置条件。不因真机暂缓而停止必要的自动回归。
2. 每个阶段有新的设备相关变化时，只在下表对应项补充范围、来源和状态；能共用一次安装与一条旅程的检查合并，不反复要求用户测试。没有设备相关变化不新增真机项目。
3. 用户明确恢复测试时，再选定一个最新、可用的 APK / 服务端提交作为共同基线集中验收。正式移动发布前仍需完成适用的设备门槛；若提前演示，明确标注未验收范围。
4. 自动测试、桌面移动视口、本地 React Bundle 和 APK 构建成功均不替代真机结果。已知失败保留到复测通过；“跳过”“未实现”“不适用”均不算通过。
5. 不自动启用插件、授予权限、开放公网或消耗新的模型预算。需要授权或收费调用时沿用原约定；无授权项目可继续保留，不阻断无关检查。

## 5. 恢复测试时的单次批次

1. 记录同批 APK 版本 / SHA-256、前后端提交、手机型号、HarmonyOS / 卓易通 / WebView 版本及权限 / 省电设置。旧 APK 结果不能自动转为新版本通过。
2. 先做 D01–D03 基础冒烟，再合并 D05 / D06 的系统能力、D07–D10 的用户旅程；复用已创建的合成材料，不上传私人聊天做测试。
3. D04 先做 10 秒诊断与短时任务，再单独安排重启、离线、跨日 / 重复；不用每个 Sprint 等待一天。涉及关闭 Docker 的场景只在用户确认不影响使用时进行。
4. 每项记录：`ID / 子场景 / 构建基线 / 初始条件 / 预期 / 实际 / 状态 / 证据 / 问题与复测版本`。状态使用“通过、失败、暂缓、跳过（原因）、不适用（原因）”。截图 / 日志不包含密钥或私人正文。
5. 修复后按受影响组定点复测，并做基础冒烟；无关且基线未变的结果可引用原证据，不机械重复全矩阵。授权、费用及长期体验仍分别记录，未满足条件的项目继续保留。

排期调整本身不要求安装手机、重打 APK 或调用收费模型，也不把未完成项改为通过；R6 / R7 等工程交付中的 Docker / 自动验收见各自报告，不能转记为手机签收。
