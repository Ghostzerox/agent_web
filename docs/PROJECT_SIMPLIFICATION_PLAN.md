# R9：去冗余、精简解耦与结构重构

- 创建日期：2026-10-18。
- 状态：R9.1–R9.2 已完成；R9.3–R9.5 待开发。R9.2 已实际删除废弃实现，未清空浏览器或服务端数据。见 [交付报告](reports/R9_2_REPORT.md)。
- 排序：R8 之后、语音 / 移动发布扩展之前；具体启动由用户下达指令。
- 优先级事实来源：[产品主线](PRODUCT_MAINLINE_GUIDE.md)。

## 1. 目的与新原则

项目以个人使用、学习与作品集为目标，不需要承担面向未知用户的永久历史兼容成本。停止以“以前实现过”“旧版本可能使用”为理由持续叠加分支、别名、适配器和双轨实现；以当前实际需要的功能组织一套清楚、可维护的实现。

当前确有兼容导出、旧数据导入、多版本契约和历史实现并存。它们是盘点对象，不代表已经证明全部冗余；具体数量、占用与删除收益由 R9.1 实测，不预先编造代码削减比例。

本阶段追求减少理解和修改成本，而不是只减少文件或行数。保留任务、专业问答、陪伴、内容、学习、娱乐和受控记忆的当前产品能力；不把模块全塞回一个大文件，不因清理破坏 R8 的总分层级或 R7 的框架 / 模板分离。

## 2. 替换原有默认兼容策略

| 对象 | 新默认策略 |
|---|---|
| 前后端与个人 APK | 支持明确的当前配套版本，不默认维护所有历史组合；必要时提示升级，而非无限增加回退分支。真机暂缓不等于旧 APK 永久受支持 |
| 用户当前数据 | 尽量一次性迁移到规范结构，再删除过渡读取路径；保留数据不等于永久保留旧实现 |
| 旧路径 / API / 导出格式 / 模板版本 | 先确认实际消费者和保存引用；无实际用途则退役。确有必要时只保留最小入口转接或有退出时间的一次性迁移，不复制编辑器 / 服务 |
| 临时兼容代码 | 必须写明用途、调用者、退出条件及所属 R9 子任务；完成迁移后移除，不能自动成为永久基础设施 |
| 后续扩展预留 | 保留少量稳定边界；没有真实使用场景的工厂、策略层、空 Provider、通用框架可删除或后移 |
| 旧测试 / 文档 / 评测快照 | 活跃入口只维护当前事实和必要回归；不强迫当前产品保留已退役行为来满足旧测试。历史证据可从 Git 查询，不靠堆叠运行时兼容保存 |

版本校验、幂等和并发控制不自动等于“历史兼容冗余”；凭据保护、真实 / 虚构隔离和草稿保护也不是仅凭代码较多就可删除的部分。允许简化它们的重复实现，不借精简删除当前必要约束。

## 3. 范围与盘点候选

下面是**待核实候选，不是预先批准全部删除的清单**：

- 旧浏览器数据 / 凭据导入、旧配置读取和一次性升级逻辑：是否已完成迁移，是否还需要常驻生产与 UI。
- 兼容名称导出（例如 R7 的 `preset.ts`）、路径别名、重复 DTO / 转换器和旧协议分支：能否统一调用者后直接移除。
- 旧移动端试验壳与当前本地 React 客户端的重复脚本 / 配置 / 构建入口；只维护当前采用的打包路径。
- 游戏旧规则与探索规则、旧快照 / 导出版本：区分独立现用玩法与单纯兼容层。d20、规则包、检查点等不能仅因早于 R7 就视为垃圾；不再需要的玩法须先明确产品取舍。
- 前后端的模式、导航、路由、工具、插件登记及校验：识别同一事实的重复维护，统一必要信息，不把授权与导航强行合成一个万能 Registry。
- 超大页面 / Manager、重复请求 / 错误 / 刷新逻辑、跨域 import：按实际责任拆分，只有确有多个调用者才提取共享实现。
- 无引用代码、过时依赖、废弃 npm 脚本、演示占位、旧诊断入口、重复测试夹具和大量阶段性文档。API、动态路由、原生桥、Worker 不能只因无静态 import 就判死代码。
- 历史 Prompt 基线：确认当前生效版本、质量证据与费用账本，再整合重复快照和断言；不篡改旧实测结论，不把删除有效覆盖当成质量改善。

数据库已应用迁移文件先不作为必删目标：当前升级有校验关系，直接删文件可能破坏启动。只有盘点证明收益明确时再单独设计迁移基线整合，覆盖现有库升级与新库安装；不为了“文件少”清空生产库。

| R9.4 依赖、工具链、测试与文档瘦身 | 移除已确认无用依赖 / 脚本 / 占位；整合夹具、当前基线、入口文档与失效指南；旧证据以 Git 或精简历史索引保留 | 一套清楚的开发 / 测试 / 构建入口；文档不重复维护相互矛盾的当前状态；有效用例仍覆盖现用能力 |
| R9.5 集成封版与结果复盘 | 当前 Web / 本地 React 构建、核心旅程、现有数据升级检查；整理前后指标、已移除支持范围与剩余问题 | 功能边界清楚，精简结果可量化、可回滚；按实际变更决定是否更新 Docker，真机继续合并暂缓，不自动扩展新功能 |

R9.1 的结论指导后续批次，而不是在盘点前承诺全面重写。纯代码清理优先；只有涉及真实数据清空、无法无损迁移或放弃仍在使用的产品能力时，再单独请求用户决定。R9 整体启动前，本规划不构成现在删除数据的授权。

## 5. 轻量实施与验收

1. 一批只解决一个明确冗余或耦合点，默认不夹带新功能，不建设重构平台。
2. 复用 Git 回滚与必要的数据备份；只涉及数据变化时才做相应迁移 / 恢复验证，不为每个别名删除重建数据库或 APK。
3. 小批次执行受影响测试、类型 / 代码检查和差异审查后提交推送；跨层或阶段封版再做完整回归与必要部署。纯文档只检查文档，不调用模型。
4. 删除废弃能力时同步删除对应失效测试，补足当前替代路径的断言；保留分支、提醒、状态一致性、引用、授权等现用契约的有效覆盖。测试数量不是越多越好，也不是越少越好。
5. 默认采用合成数据与 Mock，不调用收费模型 / Embedding，不增加测试预算；真机仍按统一待办集中执行。

R9.1 记录基线，R9.5 对照同口径指标：兼容分支 / 别名数量、重复实现和注册点、依赖 / 脚本数量、最大模块职责 / 跨层依赖、构建产物大小、构建与受影响测试耗时。行数和文件数仅作辅助，不预设削减百分比，也不以压成一行或删测伪造收益。

最终交付：当前功能 / 支持版本清单、实际删改清单、精简后的结构与开发入口、测试结果和剩余取舍。目的应是以后改一个功能需要理解更少的代码，而不是把旧复杂度换成新的抽象层。
