## 2. R6：任务模式深化与打卡

### 2.1 目标和功能

从“到点提醒 / 自动生成”深化为“计划 → 提醒 → 实际行动 → 打卡 / 完成 → 回看”。必须分清四个事实：调度已触发、AI 已执行、通知已投递、用户已完成，任何一个都不能自动替代另一个。

| 能力 | 首期范围 | 设计约束 |
|---|---|---|
| 今日任务 | 待完成、已完成、逾期 / 跳过、暂停分组；手动待办与已有定时任务关联展示 | 不以 TaskRun 成功或通知已读判断完成 |
| 打卡 / 习惯 | 每日、指定星期、每周 N 次；一次勾选或数量 / 时长目标；可写简短备注 | 计数单位明确，不把重复任务提醒变成重复打卡；周频目标和提醒时刻分开 |
| 记录管理 | 当次完成、撤销、更正、补卡、请假 / 跳过；补卡有显式标记 | 保留变更依据；不能改一天的记录来悄悄重算全部历史规则 |
| 进度回看 | 日历 / 周视图、达标率、连续与累计完成、目标进度 | 分母排除未开始、暂停及不适用日期；连续规则和跳过规则必须可解释 |
| 目标与步骤 | 一个目标拆成手动子任务或关联习惯，展示里程碑 | AI 只提出草稿，由用户确认；不自动创建提醒或判定真实行动已完成 |
| 提醒联动 | 可选关联现有普通提醒；已完成当天目标后避免无意义重复催促 | 不重建 Scheduler / Worker；修改、暂停、删除与设备快照撤销要有明确契约 |

首期按既有 `Asia/Shanghai` 计算业务日和周边界；设备时区不同不能造成重复打卡。多时区、跨凌晨作息和完整番茄钟后续按需扩展，不把游戏化积分、排行榜或强惩罚连续天数作为默认功能。

### 2.2 数据与实现思路（候选设计，实施时确定 Schema）

- 复用 [Task / TaskRun / Inbox](TASKS.md)：`scheduled_tasks` 表达调度，`task_runs` 表达系统执行；新增的用户行动与习惯记录独立建模，不能复用 Run 状态列或“主动问候 checkin”表达用户打卡。
- 候选实体：`ActionItem`（手动待办 / 目标步骤）、`Habit`、版本化 `HabitRule`、`CheckIn`（业务日、实际操作时间、数量、备注、补卡 / 撤销依据）。可选关联原 Task ID，关系及删除语义在 R6.1 定稿。
- 同一习惯同一业务日的当前记录须唯一；重试使用幂等键，数量累加与跨端版本更新分开处理，防止双击 / 手机电脑同时点击加两次。完成或撤销有操作依据，不以客户端时间独自认定完成日。
- 新规则从生效日起应用；过去记录按当时规则解释。暂停、删除、归档、补卡窗口和周起始日先写清，再做统计。清理提醒不应顺带删除用户打卡历史，硬删除需单独明确范围。
- 新增 Repository / Service / 严格 Zod DTO 与 `/api/v1` 子资源，复用错误信封、CAS 和事务；表名、路由和迁移号属于后续实现，不在本文冒充已存在。当前离线显示失败，不宣称离线打卡已同步。

## 3. R7：娱乐特化为叙事型大世界探索

### 3.1 核心取向

原有角色扮演 / AI 跑团 / 互动故事内核，新增以**世界探索**为中心的体验：选择地点 → 探索和交互 → 认识角色 / 获取物品 → 改变局势 → 形成事件与历史 → 再探索。玩家能自由输入，也能选结构化动作；不退化为只选预设选项的线性故事。

“大世界”指可持续拓展、有位置与因果关系的世界，不是首期制作 3D 引擎、无限实时模拟或完整 MMORPG。首期先用一个区域内多个相连地点完成可玩闭环，按需扩展，而不是预生成整片世界、所有 NPC 和剧情并每轮塞入 Prompt。

### 3.2 系统设计与范围

| 系统 | 计划能力 | 关键设计 |
|---|---|---|
| 地图 | 世界 / 区域 / 地点分层；连接路径、当前位置、已发现 / 已访问 / 未知、兴趣点、旅行与地标 | 首期节点图 + 可点击简图 / 列表，后续可加平面地图；已知地图与主持隐藏设定分开，移动验证相邻路径 / 条件，分支各自记录发现状态 |
| 道具 / 装备 | 背包、独立装备实例与可堆叠消耗品；装备槽、装备 / 卸下 / 使用 / 赠送 / 交易；来源、持有者、特殊能力与剧情用途 | 复用既有 inventory / items 概念，加入模板和实例区分；数量守恒、所有权、槽位与唯一物品校验；已消耗物品不能靠模型文案复活 |
| 评级 / 品质 / 等阶 / 等级 | 评级表示能力或危险的综合档位；品质表示物品 / 制作品质；等阶表示世界内的大境界 / 位阶；等级表示该等阶内的有限进度 | 四者独立定义、不混作同一数字；名称 / 排序由世界规则配置。首期简单有界，不自动引入经验条、刷怪公式或数百属性，不能把评级当成功概率 |
| 轻数值规则 | 状态、能力标签、条件、代价与叙事后果为主；必要时小规模数量 / 等级 | 默认普通移动、交谈、查看不掷骰；不确定且后果重要时才做可解释判断。骰子 / 检定为可选兼容工具，不删除旧存档的工具事件，也不只把数字藏起来保留同等复杂度 |
| 交互 | 观察、移动、交谈、询问、调查、使用、装备、交易、赠送、协助、交涉等结构化动作，加自由输入 | 当前地点 / 目标可交互对象可发现；动作产生明确结果 / 成本 / 状态变更，失败有原因；战斗首期采用轻量叙事冲突，不做完整战棋 |
| 普通 NPC | 身份、阵营、职业、当前位置、近期目标、简短性格 / 说话方式、关系与所知信息 | 可拒绝、提出条件、有自己的目标和情绪反应；活动以场景 / 回合事件触发，不让全世界 NPC 每分钟独立调用模型 |
| 重要角色 | 更丰富的角色卡、持续关系、个人故事线和关键事件参与 | 玩家角色单列；普通 NPC 可晋升重要角色，身份 ID 不变；“重要性”与 user / ai / shared 控制者是不同维度 |
| 事件 | 地方事件、角色事件、世界事件；触发前提、参与者、地点、阶段、可选行动、后果与结束条件 | 行动 / 游戏时间推进触发，防重复结算；事件变化可反映在地图、物品和关系，不靠每次重新编写设定 |
| 史诗 | 史诗篇章 / 大型故事弧、章节里程碑、关键角色、跨地区影响和多结局 | 由已发生事件累积，不强推唯一主线；允许暂不参与，避免“选择自由但每条路都是同一结局” |
| 历史 | 世界年表、时代 / 年代、地点沿革、角色传记、重大决定与后续影响 | 设定中的既往历史与玩家产生的新历史区分；已发生事实、角色传闻 / 观点、待确认传说分开，保留事件 / 回合来源 |

**重要角色卡候选字段**：身份与别名、外貌与气质、背景与经历、价值观 / 底线、说话风格、长短期目标、动机与矛盾、阵营 / 关系、对玩家的态度及变化原因、擅长能力 / 装备、日常活动与当前位置、已知信息 / 秘密、承诺 / 未解决事项、关键记忆 / 事件引用、所属故事弧。玩家公开页只显示已获知部分；主持上下文按需加载私有字段，不能让 NPC 知道未接触的秘密。

NPC 灵动不是简单扩大 Prompt：结合目标、当前情境、所知范围和关系变化生成反应，并持久化有依据的新承诺 / 行动。普通角色简卡、重要角色详卡，当前场景之外的人物只保留相关摘要，降低 Token 开销。

### 3.3 架构与兼容约束

- **沿用 GameSession 隔离域**。地图、世界史、角色关系与游戏“任务 / 日志”归娱乐，不进入用户真实任务、全局 Persona、正式长期记忆或学习记忆宫殿；跨域真实提醒只能显式提出草稿并由用户确认。
- 当前 `game-state.v2` 是严格结构，不能仅靠 Prompt 写地图或装备字段。候选新增 World / Location / Connection、ItemDefinition / ItemInstance、CharacterProfile、WorldEvent / StoryArc / Chronicle 等结构，实施时决定表与 JSONB 的合理边界。
- 世界静态模板与分支运行状态分开。位置、装备、发现、关系、NPC 承诺、事件阶段及新历史必须绑定当前祖先路径 / 快照，恢复检查点和新分支不能继承兄弟分支事实。旧回合读取采用版本适配，不批量重写历史。
- 模型产出候选叙事 / 动作 / 补丁，服务端验证地点可达、道具数量 / 归属、条件和状态转换；通过后将回合、动作结果、事件与快照原子保存。无效输出不消费道具、不记录成功交易，不对校验失败盲目重复扣费。
- 静态历史设定、角色知识可见性和“玩家已知”分别管理。历史来自回合 / 事件的可追溯引用，摘要只是派生视图，不能覆盖事实源或把传闻提升为客观历史。
- 规则包保留 Plugin API v1 边界。新增探索规则 / 状态需要显式声明版本与宿主兼容，不靠规则包 ID 分支修改核心循环。旧 d20 模板和旧会话继续可读 / 可玩；是否迁移玩法由用户选择，不自动改规则。
- 等级 / 装备 / 世界事件变更使用严格 DTO、版本锁和幂等处理；跨端 UI 共用，导出格式版本化。规则包兼容版本、状态版本和导出版本分开，不混成一个版本号。
- 上下文以“稳定世界规则 + 当前地点 / 邻接地图 + 在场角色 + 当前装备 / 相关物品 + 有关事件 / 历史片段 + 当前分支近期剧情”装配；设定、地图展示与状态操作默认不调用模型，不新增全世界定时模拟服务。

## 4. R8：单一主入口与模块内 UI 再优化

### 4.1 “互不干涉”的可执行定义

每个模块在全局导航中只有一个主入口；进入后显示该模块自己的导航和工具。不是删除子页面 URL、禁止浏览器返回或取消通知深链；它们仍指向唯一的归属页面，旧链接继续能打开并显示正确模块上下文。

**分离界面归属，不复制后端服务**：任务提醒、知识引用、文件导出可以被模块复用，但不用因此把所有工具按钮放到全局。跨模块操作显式跳转或确认，不在游戏页嵌入整套真实任务管理，也不在学习页自动改变人格 / 游戏状态。

以下为模块层级摘要；R8.1 已对照实际页面定稿，具体旧路径 / 查询 / 学习宫殿拆分以 [入口归属设计](R8_1_MODULE_ENTRY_DESIGN.md) 为准，尚未实施导航变更：

| 全局主入口 | 模块内专属入口 / 部件 | 不应常驻全局的部件 |
|---|---|---|
| 对话 | 专业 / 陪伴 / 反思切换、会话历史、资料选择、来源、摘要 / Prompt 导出、对话相关记忆 | 每种对话模式单独全局菜单、当前会话引用 / 摘要开关 |
| 任务 | 今日、打卡、习惯、目标、日历、任务记录与提醒关联 | 打卡日历、某任务子步骤、任务专用统计 |
| 学习 | 背书、解题、材料 / 错题、训练记录、学习记忆宫殿 | 训练控制、宫殿路线 / 抽测、某材料编辑器 |
| 娱乐 | 世界 / 存档选择；当前世界的地图、背包 / 装备、人物卡、事件 / 史诗 / 历史、规则包 | 地图、骰子、牌堆、物品栏、角色属性和世界史 |
| 内容 | 新闻 / 简报、书籍 / 阅读、思考问题及其订阅 / 偏好 | 每个生成器的高级参数、阅读偏好长表单 |

个人正式记忆与隐私 / 数据控制是跨模式基础能力，可从统一设置进入管理；它不是游戏史，也不是学习宫殿。`/memory` 等既有路径可保留，按页面 / 子功能标记归属，不把同名“记忆”内容混成一个全局面板。某功能需要多个上下文快捷链接时，仍落到同一页面，不创建两套编辑器。

### 4.2 结构、交互与 Sprint

- 复用 AppShell / Drawer / `appHref` / Navigation Guard；候选用小型静态模块描述表声明 `moduleId / entry / ownedRoutes / localSections`，不建设动态微前端或重写路由器。
- 全局只做模块切换、共享状态 / 设置；模块页负责本域列表、详情和操作。图标有标签 / 无障碍名，桌面与手机共用语义，手机正文优先，不嵌套多层常驻侧栏挤压空间。
- 打开导航不触发模型、存档创建、打卡、插件授权或模式变更；未保存草稿、进行中生成、冲突、空状态、离线和错误反馈保留。归属调整不是自动授予能力。
- 内容正文 / 探索叙事为主视图，地图 / 角色 / 装备作为本模块页签或抽屉；切换能回到原世界 / 当前地点，不把新导航当游戏新分支。

## 5. 交付与测试

每个 Sprint 给出实现范围、Schema / 迁移与兼容说明（如涉及）、可见旅程、定点测试、已知限制及下一步；沿用自检 / 审查 / 测试后提交和推送。文档任务只做引用、编码、结构、差异检查；实施任务按风险验证，不为每个小改动重复全量 Docker / APK 构建。

任务用合成日期 / 时钟验证业务日、重复请求、跨端冲突和统计；游戏用固定动作 / 场景和 Mock 模型验证物品守恒、分支、地图、事件与旧存档；UI 验证唯一入口、局部导航、深链、草稿和视口。主观叙事 / NPC 灵动与长期打卡收益单独验收，不以 Schema 或 Mock 满分证明体验。

新增真机检查只并入既有 D03（模块 UI）、D04 / D07（打卡关联提醒）、D05（导出）、D10（地图 / 装备 / 角色交互），开发时标注实际已实现版本；本次先登记未来范围，不启动设备测试。收费模型仍沿用既有共享预算，不因新增规划重置或自动发起调用。
